# deploy: the pull-only customer-instance stack

The deployment files the operator script
([`scripts/operator/cogeto`](../../../scripts/operator/cogeto)) installs at
`/srv/cogeto` on a fresh OVHcloud Ubuntu instance.
A customer instance **pulls the prebuilt, cosign-signed release images and
never builds**: this stack has no `build:` keys.

| File | Purpose |
| --- | --- |
| `docker-compose.deploy.yml` | The customer stack: `cogeto/cogeto`, `cogeto/cogeto-edge`, `cogeto/cogeto-mail`, `cogeto/cogeto-redaction` at `${COGETO_VERSION}`, digest-pinned infra, secrets **required** (`${VAR:?}`), `COGETO_PRODUCTION=1`, Qdrant API-key auth always on. Three optional profiles: `research`, `mail` (with its `mail-tls-sync` companion) and `redaction`. No demo / dev-seed / consoles profiles: those images are never published. |
| `Caddyfile` | Production edge: real-domain vhost + `s3.<domain>` presign origin + an ACME-only vhost for `mail.<domain>` (inert unless email capture is on), Let's Encrypt ACME, same routing and CSP as the dev Caddyfile. Mounted over the baked-in dev one. |

The operator script fetches these files (plus
`project/infra/docker/zitadel-init/init.mjs`) from the release tag that matches
the image version, generates `.env` with per-instance secrets, and brings the
stack up. Never `docker compose up` this file by hand without a populated
`.env`: every secret is required and missing values fail loudly by design.

Dev/local work keeps using the repo-root `docker-compose.yml`:
`docker compose up` on a fresh clone is the contract. When you change the
root compose or the dev Caddyfile, mirror the change here: the operator spec
(`project/src/entrypoints/operator-script.spec.ts`) asserts the two stacks
stay structurally consistent.

## The environment surface

Every value the stack reads comes from `/srv/cogeto/.env`, which the operator
script generates at install. Secrets are **required** here (`${VAR:?}`), so a
missing one fails the `compose up` loudly instead of falling back to a dev
default. `.env.example` at the repository root is the reference for every
variable, with each one marked `[installer]` (generated by the install),
`[knob]` (an operator setting) or optional.

Two families are worth calling out because they are the ones an operator adds
by hand after the install:

| Family | What it does | Absent means |
| --- | --- | --- |
| `ZITADEL_SMTP_*` | The relay Zitadel sends invitations, address verification and password resets through, applied by `zitadel-init` through the Zitadel API while it provisions. Six values: `HOST`, `USER`, `PASSWORD`, `TLS`, `FROM`, `FROM_NAME`. | No outbound identity mail at all. Nothing is configured and nothing is called, so an invitation sent from the Zitadel console silently never arrives. Initial passwords are handed over out of band. |
| `COGETO_MAIL_*` | Inbound email capture, behind the `mail` profile. | Email capture is off, and the instance runs no internet-facing SMTP listener. |

The `ZITADEL_SMTP_*` set is **all or nothing**: `HOST`, `FROM`, `FROM_NAME`
and `TLS` are required together, `USER` and `PASSWORD` are optional but must
be given together, and `TLS` must be spelled `true` or `false`. A partial set
fails the provisioning job by name rather than being half applied, because a
half-configured relay fails later at send time where nobody sees it. Applying
the same values twice converges on one configuration; changing a value
replaces it in place. The operator runbook, section 2d, has the procedure and
the recovery an already-provisioned instance needs.
