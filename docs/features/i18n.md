# Internationalisation

**V2.0 item 3.5.** How Cogeto speaks a user's language: where the strings live,
how a language is chosen, what the CI guard enforces, and how to hand a
namespace to a translator.

## The one thing to understand first

**Interface language is not extraction quality.**

Cogeto's interface can render in any language that has a locale folder. Memory
quality is a different claim, and it is measured per language (spec §14). Only
**English and Croatian** have a golden corpus and published per-language gates
today. **German and French are interface languages**: Cogeto will render its
screens and write its own copy in them, and it makes no measured claim about the
quality of facts extracted from German or French documents until a corpus and
gates exist for them.

This is stated in the product where the choice is made (Settings, under the
language selector), in [`docs/eval/gate-model.md`](../eval/gate-model.md), and on
the trust page. Nothing anywhere may imply otherwise.

## Where the strings live

```
project/web/src/locales/<locale>/<namespace>.json          the SPA
project/src/infrastructure/locales/<locale>/<ns>.json      what Cogeto writes
```

`en` is authoritative in both. `hr`, `de` and `fr` are **complete
translations**, not scaffolds: as of the F14 remediation every value in every
namespace is translated, and the CI guard fails the build if one slips back to
its English source. See [Completeness](#completeness-a-supported-locale-is-a-translated-locale).

The second root holds the copy Cogeto **writes on its own**: dreaming-digest
lines, the deterministic chat replies, the research thread message. It lives
inside `infrastructure` because that module owns it; a top-level
`project/src/locales/` would read as a bounded context to the module-boundary
rules (spec §15).

### Namespaces

One file per **product surface**, so a translator opens a small, coherent file
rather than one enormous language file. The SPA has 27 (written from
`namespaces.ts` rather than remembered):

`common` · `navigation` · `auth` · `dashboard` · `chat` · `sources` ·
`memories` · `review` · `forgotten` · `audit` · `settings` · `system` ·
`providers` · `capabilities` · `approvals` · `skills` · `research` ·
`timeline` · `passport` · `reports` · `email` · `extraction` ·
`connections` · `projects` · `errors` · `validation` · `serverErrors`

`serverErrors` is the odd one: it is not a surface but **one key per server
error code**, and its `en` file is GENERATED from the server's throw sites by
`npm run i18n:server-errors`. Translate it like any other; never hand-edit its
English.

The server catalogue has four: `digest` · `chat` · `report` · `research`.

Adding a namespace means adding it to
[`project/web/src/i18n/namespaces.ts`](../../project/web/src/i18n/namespaces.ts)
**and** creating the file in every locale. `npm run i18n:check` fails otherwise.

### Keys

Keys are **structural**: they name the meaning and the location, never the
English content.

```
sources.detail.emptyState.title     good: survives any rewording
noMemoriesYet                       bad: rewording English invalidates it
```

Rewording the English source must never invalidate a translation, which is only
true if the key does not encode the English.

## How a language is chosen

Highest precedence first:

1. the user's stored `preferred_language` setting,
2. the browser's preference, narrowed to a locale Cogeto ships,
3. English.

(2) applies only while (1) is unknown: signed out, or the context request still
in flight. **Nothing detects and overrides an explicit choice.** There is
deliberately no `i18next-browser-languagedetector`.

Changing the language in Settings **applies without a page reload**: the save
invalidates the `['user-context']` query, `useInterfaceLanguage` sees the new
value, loads the locale bundle and calls `changeLanguage`, and every subscriber
re-renders.

English is bundled eagerly because it is the fallback for every key in every
locale. The other locales are lazy chunks, fetched the first time they are
selected, so a monolingual instance never downloads three unused languages.

`preferred_language` is one setting, not two: it selects the interface language
**and** the language of everything Cogeto initiates. Reply mirroring and strict
mode are unchanged by this work: a reply still mirrors the language of the
message it answers, unless strict mode forces the anchor.

## Mechanics

**Interpolation is named**, never positional:

```json
{ "captured": "captured {{when}}" }
```

**Plurals go through CLDR**, with i18next's suffix keys. This is not decoration:
Croatian has more plural forms than English.

```json
{
  "removed": {
    "memories_one": "{{count}} memory",
    "memories_other": "{{count}} memories"
  }
}
```

Croatian needs `_one`, `_few` and `_other`; French needs `_one`, `_many` and
`_other`; German and English need `_one` and `_other`. The scaffolding command
expands them for you, and the check verifies each locale carries exactly the
categories **its own** rules require, asking `Intl.PluralRules` rather than a
hardcoded table.

**No sentence assembly from fragments.** Word order differs across languages, so
a full sentence is one key with interpolated values. Where part of a sentence
needs markup, the markup is a slot in the value and `<Trans>` fills it:

```json
{ "source": "Source: <kind>{{kind}}</kind>" }
```

**Enumerations**: lifecycle statuses, uncertainty sub-reasons, capability states,
job states, approval statuses, file states, refusal reasons. Their **values** are
the API's and travel unchanged; only their **display names** are translated, via
an explicit value → key map. A translated label is never sent to an API.

## Formatting

Every date, time, relative time, number and file size goes through
[`project/web/src/i18n/format.ts`](../../project/web/src/i18n/format.ts), which
takes the **active interface locale** and maps it to a BCP-47 tag
(`LOCALE_TAGS`). `en` maps to `en-GB`, which is what the one hardcoded `en-GB`
site already produced, so English renders exactly as before.

Before this, most call sites used `toLocaleDateString()` with no locale, so
formatting followed the browser rather than the user's choice, and one site was
hardcoded to `en-GB` (an audit finding). Both are now gone.

Timezone handling is untouched: the instance-context now-block is server-side and
unchanged.

## The CI guard

`npm run i18n:check` runs inside `npm run lint`, so it is part of the required
`lint` check. It fails the build, naming the exact keys, per locale, per
namespace, on:

1. **Key sync**: a base key in `en` missing from another locale, or a key in
   another locale that `en` does not have. Namespace files must match too.
2. **Plural completeness**: a plural key missing a category the locale's own CLDR
   rules require, or carrying one they do not have.
3. **Placeholder parity**: a translated value that dropped a `{{variable}}` or a
   `<tag>`. Nobody catches that by eye in a language they do not read.
4. **House style**: an em or en dash in an English source value, the same rule
   `copy/no-typographic-dashes` enforces over the code, extended to the locale
   files (ESLint does not parse JSON).
5. **Unused keys**: an English key no source file references.
6. **Completeness**: a value that is still its English source, in a locale
   Cogeto ships as supported. See below.
7. **Server error codes**: a coded failure with no interface key, an interface
   key no throw site raises, or English at the throw site that has drifted from
   the key translators worked from. See below.
8. **Hardcoded literals**: exactly, on the server; heuristically, in the SPA.

Every one of these is proved by breaking it:
[`project/src/entrypoints/i18n-guard.spec.ts`](../../project/src/entrypoints/i18n-guard.spec.ts)
copies the repository, introduces one deliberate regression per category, runs
the real script against the copy, and asserts it fails naming the offence. A
check that is never observed to fail is a claim, not a check.

### Completeness: a supported locale is a translated locale

**An untranslated value is a value identical to its English source.** That is
the whole rule, and it is what F14 needed: `hr`, `de` and `fr` shipped as
supported interface languages while 42 to 45% of their values were still
literal English, unevenly, so a Croatian user's Sources page was English while
their Chat page was Croatian.

A value may legitimately equal its English source, and that case is an explicit,
reviewable entry in
[`scripts/ci/i18n-identical.json`](../../scripts/ci/i18n-identical.json):
`Cogeto`, `PDF`, `{{count}} {{noun}}`, `Signature (ed25519, base64)` in French.
The list stays short because **an entry that excuses nothing is a build error**:
once every locale translates a key, its entry has to go.

On success the check prints the coverage it just proved, per locale, so a
number a reader can compare against last week's ends up in the build log:

```
check-i18n: 3 locales in sync and fully translated
  (de 1933/1933 · fr 2015/2015 · hr 2015/2015 values translated, 112 identical by design).
```

### What the literal detector does and does not catch

Honesty about coverage matters more than the appearance of it.

**On the server it is exact, not heuristic.** There is one legal way to raise
an HTTP failure (`userError` or `untranslatedError`, see
[Server errors](#server-errors-are-codes-not-sentences)), so constructing a
Nest exception anywhere else fails the build. That is what closed F13: the scan
used to stop at the SPA boundary, and 197 English server sentences were
invisible to it by construction. The single deliberate exception is a line
preceded by `// i18n-exempt: <reason>`, which puts the decision in the diff.

**In the SPA it catches**: English JSX text of two words or more between tags,
and English strings of two words or more assigned to `placeholder`, `title`,
`aria-label`, `aria-description`, `alt` and `label`, in `project/web/src`,
outside specs. The threshold was three words until this work; two catches
"Save changes" and "No results yet", and produced no false positive on the
current tree.

**It does not catch**:

- single words (`Save`, `Cancel`): indistinguishable from identifiers, class
  names, enum values and CSS tokens at this level of analysis;
- text built at runtime from variables, including a template literal;
- strings passed as ordinary function arguments or object values, which is
  where a reintroduced literal is most likely to hide today;
- text inside a `<Trans>` child element;
- the server's non-HTTP output: log lines, prompt assembly, the receipt and
  report payloads, and the CLI. Those are not copy, and treating them as copy
  would bury the real findings.

The SPA half is a regression net for the common shape of a reintroduced
literal, not proof of coverage. Key sync, the completeness count and the
server-code parity carry the weight.

### Loud missing keys

In a development build a missing key renders as `«namespace:key»` and is logged
once with `console.error`. The switch is overridable at runtime without a
rebuild, so the same check can be run against a real deployment:

```js
localStorage.setItem('cogeto.i18n.debug', 'on'); // force on, then reload
localStorage.setItem('cogeto.i18n.debug', 'off'); // force off
localStorage.removeItem('cogeto.i18n.debug'); // back to the build default
```

## Server errors are codes, not sentences

**Audit finding F13.** Two hundred exception sites across `project/src` carried
hardcoded English, the interface rendered `error.message` verbatim at several
dozen places, and no check could see any of it. A Croatian page showed English
error text in the middle of itself.

### The mechanism, and why

The server answers a failed request with its usual body plus two fields:

```json
{ "statusCode": 404, "error": "Not Found",
  "message": "memory 7f3c not found",
  "code": "memory.notFound", "params": { "id": "7f3c" } }
```

`code` is a **stable identifier** the interface maps to a key in its own
`serverErrors` namespace; `params` are the values that key's translation places
wherever its own word order puts them. `message` stays English and stays
exactly what it was: the log line, the answer for a client that is not our SPA,
and the fallback the interface renders for a code it holds no key for.

The alternative was producing the message server-side in the requester's
language, through the same `serverT` catalogue the digest and the deterministic
chat replies use. Three things in this codebase decided against it:

1. Most of these exceptions are thrown from stores and services with no
   `Principal` in scope (`memory.store.ts`, `import.service.ts`,
   `provider-config.service.ts`). Producing text in the requester's language
   would mean threading a locale through several hundred call sites; a code
   needs nothing threaded.
2. The server's language stays independent of the client's. One code path
   answers a Croatian SPA, an English operator script and a machine client.
3. The interface can phrase an error to suit the surface it appears on. A code
   survives that; a finished sentence does not.

The codebase had already reached the same conclusion where it needed the client
to react: the daily-quota and stream-limit failures shipped a `code` field long
before this work, and `skill-engine.ts` branches on `daily_research_limit`.
Those six codes keep their original spelling, because a code is a contract once
a client reads it.

### User-facing or not: the rule

The question is not "is this an error" but **"will a person read this sentence,
and can we write it for them?"**

`userError` when a person using the interface can cause the failure and would
act on the answer: a name left blank, a file too large, a state that forbids
the action, a limit reached, a thing that is gone.

`untranslatedError` in exactly three situations, and no others:

1. **A developer error.** The failure means our own code is wrong, or a request
   arrived in a shape our own interface never sends (`'body must be { key }'`).
   Nobody but an engineer benefits from the words, and translating it would
   dress a bug up as an ordinary answer.
2. **A machine client.** Nothing renders the body: the mail intake token guard,
   the health-endpoint token guard, a webhook signature. No person, no locale.
3. **Text we did not write.** A model provider's own error, a validation
   library's own message, passed through verbatim.

When it is genuinely both, the code goes on the frame and the upstream words
travel as a parameter (`search_unavailable` is the example).

### Writing one

```ts
throw userError.notFound('memory.notFound', 'memory {{id}} not found', { id });
throw userError.badRequest(
  'import.uploadsUnfinished',
  { one: '{{count}} file has not finished uploading',
    other: '{{count}} files have not finished uploading' },
  { count: unstaged.length },
);
```

A value inside a message is `{{named}}`, **never** a template literal: Croatian
and German put those values in different places in the sentence, and a value
baked into the string cannot move. The scanner refuses a template containing
`${`.

Then regenerate the interface's copy of the English and backfill the locales:

```sh
npm run i18n:server-errors   # rewrites en/serverErrors.json from the throw sites
npm run i18n:sync            # backfills the other locales, then translate them
```

The English sentence exists twice on purpose, at the throw site and in
`en/serverErrors.json`. That is safe because `i18n:check` reads both and fails
the build on a byte of difference.

### Rendering one

The interface never renders `error.message` where it holds a translation.
[`project/web/src/i18n/api-error.ts`](../../project/web/src/i18n/api-error.ts)
resolves the code and degrades in this order: the translation; the server's own
English sentence for a code we have no key for; the caller's fallback key; the
generic `errors:server.unexpected`. Never a bare code, never an empty string.

```tsx
const apiError = useApiErrorMessage(t);
…
{apiError(save.error, 'anchor.saveFailed')}
```

**Known limitation, stated rather than hidden:** a parameter that happens to be
an enum value travels raw, so `a {{state}} connector cannot sync` renders the
state word in English inside an otherwise Croatian sentence. There are four
such sites (connector state, import item state). Translating parameter values
would need the server to say which parameters are enums and of what type;
that is a real design, and it is not this one.

## Adding a string to an existing feature

The everyday case, and the one the rules bind:

```sh
# 1. add the key to en, and use it in the code
# 2. backfill every other locale
npm run i18n:sync          # or --dry to see what it would do first
# 3. confirm and commit
npm run i18n:check
```

`i18n:sync` adds every key `en` has and a locale lacks, with the **English text
as the value**, and expands the plural forms that language needs: an English
`_one`/`_other` pair becomes `_one`/`_few`/`_other` in Croatian and
`_one`/`_many`/`_other` in French, seeded from English `_other`. It also removes
orphans, so run `--dry` first if you might be deleting a translation.

Two things it will never do:

- **It never overwrites an existing value** (except under `--refresh`, below).
  A translated string is left alone, always. That is what separates it from
  `i18n:add --force`, which resets a whole locale to English.
- **It never translates.** Machine translation landing in product copy with
  nobody reviewing it is a person's decision, not a build script's. The English
  placeholder is correct in the meantime: the runtime falls back to English
  anyway, so an untranslated key renders readable copy, never a raw key.

## Rewording English: the drift the key checks could not see

The checks above compare **key sets**, plural categories and placeholders.
None of them looks at whether the WORDS are current, and `i18n:sync` never
overwrites a value. So for a while, **rewording an English string left every
other locale serving the previous wording, with a green build.** It shipped
once, in V2.5 item 8.3, and was found by diffing the built bundle against
`en`, which is not a process anyone should rely on.

The invariant that makes it checkable: **an untranslated value equals the
current English; a deliberately translated one is registered with the English
it was made from.** The register is `<root>/.translations.json`, beside the
locale directories so a translator's folder still holds only their namespace
files:

```json
{ "de": { "capabilities": { "capability.demo.name": "Demo sandbox" } } }
```

`i18n:check` then reports two distinct failures, each with its own remedy:

| Failure | What it means | Fix |
|---|---|---|
| `STALE "<key>"` | The value is neither today's English nor a registered translation, so it is the PREVIOUS English left behind by a reword. | `npm run i18n:sync -- --refresh` takes the current English into every unregistered value. |
| `OUTDATED translation "<key>"` | A real translation whose source moved: the words still read well and now translate something English no longer says. | Retranslate, then `npm run i18n:sync -- --register`. |

`--register` records every value that currently differs from English as a
deliberate translation. Run it after finishing a namespace; that is what
protects the work from `--refresh`, which only ever touches unregistered
values.

**Stated honestly:** the register was seeded from the state of the repository
on the day it was introduced, so the 2752 existing translations are recorded
as matching the English of that day. Drift is caught from then on; drift that
predates the register is not, because nothing recorded what those strings were
translated from.

## Adding a locale

One command, then translation:

```sh
npm run i18n:add -- es
```

It copies every namespace from `en` into both roots, keeping the same keys and
the **English text as the value**, and expands the plural forms the new language
needs. Then:

1. add the code to `SUPPORTED_LANGUAGES`, `LANGUAGE_ENDONYMS` and `LOCALE_TAGS`
   in [`project/shared/src/user-context.ts`](../../project/shared/src/user-context.ts);
2. translate the values (below);
3. run `npm run i18n:check` and switch a user to the new language.

An untranslated locale renders correctly from step 1: every value is English, and
anything missing falls back to English anyway.

## For the translator

Read this before starting. It is written for whoever does the translation later,
with a model or by hand.

- **Where**: `project/web/src/locales/<locale>/` and
  `project/src/infrastructure/locales/<locale>/`. One file per surface.
- **What a namespace is**: one product surface. `review.json` is everything the
  Contradictions page can render. Translate one file at a time.
- **The English value is the source text.** Every file already contains English
  in every slot. You overwrite the values. You never touch the keys.

**Never translate:**

| Thing                       | Example                                    |
| --------------------------- | ------------------------------------------ |
| Keys                        | `drawer.panel.actions`                     |
| Interpolation variables     | `{{count}}`, `{{subject}}`, `{{when}}`     |
| Markup slots                | `<b>`, `<link>`, `<q>`, `<n>`             |
| Enum values inside keys     | `memoryStatus.user_approved`               |
| Brand and product names     | Cogeto, Zitadel, MinIO, Qdrant, PostgreSQL |
| The tagline                 | "Models are rented. Knowledge is owned."   |
| File paths, URLs, commands  | `docs/passport-schema/`, `cogeto features` |

**Plural forms**: a key ending `_one`, `_few`, `_many` or `_other` is a plural
form. Your language's file already has exactly the forms your language needs;
fill each one with the correct wording for that count. Do not add or remove
forms: the check knows which ones your language requires.

### The instruction to hand a model, per file

> Translate the JSON below from English into <LANGUAGE>.
>
> - Translate **values only**. Never change a key.
> - Preserve every interpolation placeholder verbatim: `{{name}}` stays
>   `{{name}}`, in the position that reads naturally in <LANGUAGE>.
> - Preserve every markup tag verbatim: `<b>`, `<link>`, `<q>` and their closing
>   tags must all survive, wrapping the same meaning.
> - Do not translate: Cogeto, product names (Zitadel, MinIO, Qdrant,
>   PostgreSQL), file paths, URLs, shell commands, or the tagline "Models are
>   rented. Knowledge is owned."
> - Keys ending `_one`, `_few`, `_many`, `_other` are plural forms. Write each
>   one with the wording that is correct for that count in <LANGUAGE>. Do not add
>   or remove plural keys.
> - Tone: plain, professional, direct. Second person. No exclamation marks that
>   are not in the source.
> - If a term of art has no confident translation, **leave the English value
>   unchanged** rather than guessing.
> - Return the complete JSON object, valid and nothing else.

### Verifying a locale

```sh
npm run i18n:check     # keys, plurals, placeholders, source drift
```

Then switch a user to the language in Settings and walk the app. Nothing should
show a raw key or a `«missing»` marker; anything untranslated shows English,
which is correct, not a bug.
