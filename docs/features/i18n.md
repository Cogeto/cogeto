# Internationalisation

**V2.0 item 3.5.** How Cogeto speaks a user's language: where the strings live,
how a language is chosen, what the CI guard enforces, and how to hand a
namespace to a translator.

## The one thing to understand first

**Interface language is not extraction quality.**

Cogeto's interface can render in any language that has a locale folder. Memory
quality is a different claim, and it is measured per language (spec §14). Only
**English and Croatian** have a golden corpus and published per-language gates
today. **German and French are interface languages**: Cogeto will render its
screens and write its own copy in them, and it makes no measured claim about the
quality of facts extracted from German or French documents until a corpus and
gates exist for them.

This is stated in the product where the choice is made (Settings, under the
language selector), in [`docs/eval/gate-model.md`](../eval/gate-model.md), and on
the trust page. Nothing anywhere may imply otherwise.

## Where the strings live

```
project/web/src/locales/<locale>/<namespace>.json          the SPA
project/src/infrastructure/locales/<locale>/<ns>.json      what Cogeto writes
```

`en` is authoritative in both. `hr`, `de` and `fr` exist as complete files.

The second root holds the copy Cogeto **writes on its own**: dreaming-digest
lines, the deterministic chat replies, the research thread message. It lives
inside `infrastructure` because that module owns it; a top-level
`project/src/locales/` would read as a bounded context to the module-boundary
rules (spec §15).

### Namespaces

One file per **product surface**, so a translator opens a small, coherent file
rather than one enormous language file. The SPA has 21:

`common` · `navigation` · `auth` · `dashboard` · `chat` · `sources` ·
`memories` · `review` · `forgotten` · `audit` · `settings` · `system` ·
`capabilities` · `approvals` · `skills` · `research` · `timeline` · `passport` ·
`email` · `errors` · `validation`

The server catalogue has three: `digest` · `chat` · `research`.

Adding a namespace means adding it to
[`project/web/src/i18n/namespaces.ts`](../../project/web/src/i18n/namespaces.ts)
**and** creating the file in every locale. `npm run i18n:check` fails otherwise.

### Keys

Keys are **structural**: they name the meaning and the location, never the
English content.

```
sources.detail.emptyState.title     good: survives any rewording
noMemoriesYet                       bad: rewording English invalidates it
```

Rewording the English source must never invalidate a translation, which is only
true if the key does not encode the English.

## How a language is chosen

Highest precedence first:

1. the user's stored `preferred_language` setting,
2. the browser's preference, narrowed to a locale Cogeto ships,
3. English.

(2) applies only while (1) is unknown: signed out, or the context request still
in flight. **Nothing detects and overrides an explicit choice.** There is
deliberately no `i18next-browser-languagedetector`.

Changing the language in Settings **applies without a page reload**: the save
invalidates the `['user-context']` query, `useInterfaceLanguage` sees the new
value, loads the locale bundle and calls `changeLanguage`, and every subscriber
re-renders.

English is bundled eagerly because it is the fallback for every key in every
locale. The other locales are lazy chunks, fetched the first time they are
selected, so a monolingual instance never downloads three unused languages.

`preferred_language` is one setting, not two: it selects the interface language
**and** the language of everything Cogeto initiates. Reply mirroring and strict
mode are unchanged by this work: a reply still mirrors the language of the
message it answers, unless strict mode forces the anchor.

## Mechanics

**Interpolation is named**, never positional:

```json
{ "captured": "captured {{when}}" }
```

**Plurals go through CLDR**, with i18next's suffix keys. This is not decoration:
Croatian has more plural forms than English.

```json
{
  "removed": {
    "memories_one": "{{count}} memory",
    "memories_other": "{{count}} memories"
  }
}
```

Croatian needs `_one`, `_few` and `_other`; French needs `_one`, `_many` and
`_other`; German and English need `_one` and `_other`. The scaffolding command
expands them for you, and the check verifies each locale carries exactly the
categories **its own** rules require, asking `Intl.PluralRules` rather than a
hardcoded table.

**No sentence assembly from fragments.** Word order differs across languages, so
a full sentence is one key with interpolated values. Where part of a sentence
needs markup, the markup is a slot in the value and `<Trans>` fills it:

```json
{ "source": "Source: <kind>{{kind}}</kind>" }
```

**Enumerations**: lifecycle statuses, uncertainty sub-reasons, capability states,
job states, approval statuses, file states, refusal reasons. Their **values** are
the API's and travel unchanged; only their **display names** are translated, via
an explicit value → key map. A translated label is never sent to an API.

## Formatting

Every date, time, relative time, number and file size goes through
[`project/web/src/i18n/format.ts`](../../project/web/src/i18n/format.ts), which
takes the **active interface locale** and maps it to a BCP-47 tag
(`LOCALE_TAGS`). `en` maps to `en-GB`, which is what the one hardcoded `en-GB`
site already produced, so English renders exactly as before.

Before this, most call sites used `toLocaleDateString()` with no locale, so
formatting followed the browser rather than the user's choice, and one site was
hardcoded to `en-GB` (an audit finding). Both are now gone.

Timezone handling is untouched: the instance-context now-block is server-side and
unchanged.

## The CI guard

`npm run i18n:check` runs inside `npm run lint`, so it is part of the required
`lint` check. It fails the build, naming the exact keys, per locale, per
namespace, on:

1. **Key sync**: a base key in `en` missing from another locale, or a key in
   another locale that `en` does not have. Namespace files must match too.
2. **Plural completeness**: a plural key missing a category the locale's own CLDR
   rules require, or carrying one they do not have.
3. **Placeholder parity**: a translated value that dropped a `{{variable}}` or a
   `<tag>`. Nobody catches that by eye in a language they do not read.
4. **House style**: an em or en dash in an English source value, the same rule
   `copy/no-typographic-dashes` enforces over the code, extended to the locale
   files (ESLint does not parse JSON).
5. **Unused keys**: an English key no source file references.
6. **Hardcoded literals** in the SPA.

### What the literal detector does and does not catch

Honesty about coverage matters more than the appearance of it.

**It catches**: multi-word English JSX text between tags, and multi-word English
strings assigned to `placeholder`, `title`, `aria-label`, `alt` and `label`, in
`project/web/src`, outside specs.

**It does not catch**:

- single words (`Save`, `Cancel`): indistinguishable from identifiers, class
  names, enum values and CSS tokens at this level of analysis;
- text built at runtime from variables;
- strings passed as ordinary function arguments or object values;
- anything outside the SPA.

It is a regression net for the common shape of a reintroduced literal, not proof
of coverage. Key sync and the missing-key reporter carry the weight.

### Loud missing keys

In a development build a missing key renders as `«namespace:key»` and is logged
once with `console.error`. The switch is overridable at runtime without a
rebuild, so the same check can be run against a real deployment:

```js
localStorage.setItem('cogeto.i18n.debug', 'on'); // force on, then reload
localStorage.setItem('cogeto.i18n.debug', 'off'); // force off
localStorage.removeItem('cogeto.i18n.debug'); // back to the build default
```

## Adding a locale

One command, then translation:

```sh
npm run i18n:add -- es
```

It copies every namespace from `en` into both roots, keeping the same keys and
the **English text as the value**, and expands the plural forms the new language
needs. Then:

1. add the code to `SUPPORTED_LANGUAGES`, `LANGUAGE_ENDONYMS` and `LOCALE_TAGS`
   in [`project/shared/src/user-context.ts`](../../project/shared/src/user-context.ts);
2. translate the values (below);
3. run `npm run i18n:check` and switch a user to the new language.

An untranslated locale renders correctly from step 1: every value is English, and
anything missing falls back to English anyway.

## For the translator

Read this before starting. It is written for whoever does the translation later,
with a model or by hand.

- **Where**: `project/web/src/locales/<locale>/` and
  `project/src/infrastructure/locales/<locale>/`. One file per surface.
- **What a namespace is**: one product surface. `review.json` is everything the
  Contradictions page can render. Translate one file at a time.
- **The English value is the source text.** Every file already contains English
  in every slot. You overwrite the values. You never touch the keys.

**Never translate:**

| Thing                       | Example                                    |
| --------------------------- | ------------------------------------------ |
| Keys                        | `drawer.panel.actions`                     |
| Interpolation variables     | `{{count}}`, `{{subject}}`, `{{when}}`     |
| Markup slots                | `<b>`, `<link>`, `<q>`, `<n>`             |
| Enum values inside keys     | `memoryStatus.user_approved`               |
| Brand and product names     | Cogeto, Zitadel, MinIO, Qdrant, PostgreSQL |
| The tagline                 | "Models are rented. Knowledge is owned."   |
| File paths, URLs, commands  | `docs/passport-schema/`, `cogeto features` |

**Plural forms**: a key ending `_one`, `_few`, `_many` or `_other` is a plural
form. Your language's file already has exactly the forms your language needs;
fill each one with the correct wording for that count. Do not add or remove
forms: the check knows which ones your language requires.

### The instruction to hand a model, per file

> Translate the JSON below from English into <LANGUAGE>.
>
> - Translate **values only**. Never change a key.
> - Preserve every interpolation placeholder verbatim: `{{name}}` stays
>   `{{name}}`, in the position that reads naturally in <LANGUAGE>.
> - Preserve every markup tag verbatim: `<b>`, `<link>`, `<q>` and their closing
>   tags must all survive, wrapping the same meaning.
> - Do not translate: Cogeto, product names (Zitadel, MinIO, Qdrant,
>   PostgreSQL), file paths, URLs, shell commands, or the tagline "Models are
>   rented. Knowledge is owned."
> - Keys ending `_one`, `_few`, `_many`, `_other` are plural forms. Write each
>   one with the wording that is correct for that count in <LANGUAGE>. Do not add
>   or remove plural keys.
> - Tone: plain, professional, direct. Second person. No exclamation marks that
>   are not in the source.
> - If a term of art has no confident translation, **leave the English value
>   unchanged** rather than guessing.
> - Return the complete JSON object, valid and nothing else.

### Verifying a locale

```sh
npm run i18n:check     # keys, plurals, placeholders
```

Then switch a user to the language in Settings and walk the app. Nothing should
show a raw key or a `«missing»` marker; anything untranslated shows English,
which is correct, not a bug.
