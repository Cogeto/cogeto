# The Memory Passport

One click exports everything Cogeto holds for you **in one space**, in a published open
format, that a third party can verify without any Cogeto code or service. This is the
anti-lock-in promise made concrete: leave whenever you want.

**A passport is per space** (docs/features/spaces.md section 5 as amended): the export
covers the space you triggered it from, the manifest names that space, and the receipts
it carries belong to that space's own chain. A receipt in the export never references a
receipt from another space, because since the chains became per space no receipt
anywhere does.

Precisely what "verifiable standalone" means here: **every receipt in the archive
verifies individually** from the archive and the shipped public key alone, because the
signature covers the canonical payload including its `prev_hash` link. A full
genesis-to-tip WALK of the space's chain from the archive alone additionally requires
that every receipt in the space is yours: the export carries the exporting owner's
receipts, and in a space where colleagues also erased material, the walk would cross
their receipts, which the export must not contain. In that case the links between your
receipts are still attested by the signatures; re-walking the whole chain offline needs
the instance (GET /api/receipts/verify), which walks it server-side.

The published schemas and the verification steps live in
[`../passport-schema/`](../passport-schema/).

## A zip of JSON documents plus a signed manifest

Not a single JSON blob, because the full archive can carry binary originals and
base64-embedding them would inflate size by about a third while making the export
unreadable as plain files. A zip keeps every document independently openable and
hashable.

Entries are **stored uncompressed**, so a document's bytes in the archive are
byte-for-byte the bytes the manifest hashed. Nothing needs decompressing to verify. The
writer is dependency-free, which keeps the format fully in our control.

```
manifest.json         signed index: version, timestamp, public key, per-document sha256
manifest.json.sig     detached ed25519 signature over manifest.json's exact bytes
memories.json         every memory, full history and supersession pointers
receipts.json         deletion receipts with chain hashes, signatures, and the public key
README.txt            human pointer to the schema and how to verify
attachments/…         original file bytes, only when the user opts in
```

## Versioned, and old versions stay readable

The format is open: JSON Schema plus a human spec, versioned by `passport_version` and
stamped into every document. The in-code Zod contract and the published schema are kept
in lockstep, and a test re-validates real generated bytes against the published schema,
so drift fails the build.

A breaking change bumps the version and publishes a new schema directory; **old
versions stay published and stay valid**. An archive exported under an earlier version
remains a complete, verifiable artifact, because verification uses the bytes and the key
inside the archive and never the server. The validator accepts only the current version
for new exports: an instance writes one version, and readers pick the schema directory
matching the archive's own `passport_version`.

The current version is **2.1**, which added the required `space` block to the manifest
(the passport became per space). Version 2.0 lacked it; version 1.0 additionally carried
a required `tasks` document. Each change was handled as a version bump rather than
improvised, and every earlier version stays published and verifiable.

## The complete record, not the current state

- **memories.json** carries every memory you may see, in **any** lifecycle status,
  `replaced` and `outdated` included, each with content, status, scope, sensitivity,
  entities, subject, kind, both interval bounds, and `superseded_by`. The full validity
  history and every supersession chain reconstruct from the export alone, with no server.
- **Provenance** is reference-level: every memory carries its `source_type` and
  `source_id`, plus file metadata for your own uploads and an attachment path when
  originals are included. Cogeto's durable representation is the extracted fact, so the
  fact carries the substance and the reference locates the source.
- **receipts.json** carries your confirmed deletion receipts in exactly the shape the
  chain verifier consumes, plus the instance public key, so each receipt stays
  independently verifiable against its chain outside Cogeto.

## Originals are opt-in

Original files are **reference-only by default**: metadata and provenance, no bytes. A
per-export toggle attaches the originals of your own uploads. The common case is a
compact, portable record; the full binary archive is an explicit choice.

## Gating

The export runs a **worker job that re-reads through the same Principal-gated
interfaces** as every other read, so it can only ever include what you are entitled to
see.

| | |
| --- | --- |
| Own private data | included |
| Shared data you can legitimately see | included, marked not-owned-by-you with its owner |
| Another user's private data | never |
| Another user's original file bytes | never; attachments resolve for your own uploads only |
| Your own sensitive data | included and clearly marked |
| A teammate's sensitive data | never, even when shared |

## Verification

The manifest lists every document with its SHA-256 and byte length, and is itself
signed with the instance key. The export's integrity verifies **exactly like a deletion
receipt**:

1. Verify the manifest signature against the manifest bytes using the included public
   key, cross-checking that key against the instance's public-key endpoint.
2. SHA-256 each listed document and compare hash and length.
3. Verify each receipt against its hash chain and the key.

## Delivery

The artifact is written under an owner-scoped key covered by the bucket's default
encryption, and delivered as a **short-lived presigned URL** from an owner-gated
endpoint. Export objects are excluded from the orphan sweep, since they are not
metadata-backed, and are reclaimed by an hourly retention pass that deletes the object
and marks the row expired after 24 hours. The "short-lived" promise is enforced, not
asserted.

The request ledger the SPA polls holds no memory content.
